## 3. What We Struggled With

1. **Append-only trigger surprise** — Migration 0191 introduced a trigger with business-logic side effects (`ap_reconciliation_snapshots_append_only`). This violated the "no new business DB triggers" rule (AGENTS.md §C) and caused the `ON DUPLICATE KEY` pivot in Story 55.1. The trigger was not visible in any schema documentation accessible to the dev team during the spike.

2. **Schema-correctness gaps** — 2/5 story specs (55.2, 55.4) had ACs referencing field names that didn't match the real DB schema (`event` vs `action_type`, `created_by` vs `changed_by`, `SNAPSHOT_SUPERSEDED` vs `RECALCULATED`). Caught in second-pass review. Epic charter had same drift.

3. **E51-A1 sat idle for 4 epics** — the action item was tracked but no one worked it until Epic 55 organically needed the same fix. Tracking ≠ doing.

4. **Archive flow deferred** — the trigger constraint blocks the archive/retention flow for both AP and AR. Deferred as P3, but will become P1 when AR work begins.

---

## 4. Key Insights

1. **The "no business DB triggers" rule has no CI enforcement** — any migration can add a trigger that enforces business logic, bypassing the rule. A lint gate is needed.

2. **Three sources of truth created inconsistency risk** — epic charter, story spec, and real DB schema all had slight disagreements on field names and event types. A single source of truth (generated from schema) would eliminate this.

3. **Concurrent simulation tests are the correctness proof that matters** — not unit tests, not integration tests with sequential calls. Parallel concurrent calls proving idempotency.

4. **Deferred action items don't get done unless they become someone's immediate problem** — E51-A1 is the clearest example.

5. **`toUtcIso.dateLike({ nullable: true })` is a common nullable-handling pattern we keep getting wrong** — appeared independently in 55.1 and 55.4.
